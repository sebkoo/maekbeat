# Hazard analysis

Maekbeat is not a medical device, and this is not a risk management file. It is
an exercise: the structure ISO 14971 asks for, applied to an educational
codebase, to show the practice rather than to claim conformance. Read
[README.md](README.md) in this directory first — it states what this is, what it
is not, and what a real submission would need that this has none of.

Every row below is populated from something that actually happened here. None of
these hazards was imagined for the document; each is a defect this repository
found, fixed, and pinned with a test, and the row cites that test.

## The citation is checked

`scripts/check-hazard-tests.sh` reads this file and fails the build when a row
cites nothing, when a cited file is missing, when the cited test is not declared
in it, or when the cited file contains a skipped or `.only` test. It runs in the
CI hygiene job (`.github/workflows/ci.yml`) and under `/ship-check`.

That guard is the argument for this document existing. A hazard table nothing
checks drifts out of true the first time a test is renamed, and reads exactly the
same afterwards. Its mutation proofs are in
[../ai/mutation-log.md](../ai/mutation-log.md).

What it does not check: that the cited test is a _good_ test, that it actually
exercises the control named beside it, or that the control is adequate. It checks
that the citation resolves to a test that runs. The judgement stays human — this
removes one failure mode, the silent kind.

## Terms

Used the way ISO 14971:2019 uses them, as far as I could verify them — the
standard is paywalled and I could not read the primary text, so the definitions
below are my own words and the clause numbers are absent on purpose. See
"Citations I could not verify" in [README.md](README.md).

- **Hazard** — a potential source of harm.
- **Foreseeable sequence of events** — the chain, starting from ordinary use or
  ordinary failure, by which the hazard reaches somebody.
- **Harm** — injury or damage to health. Named in clinical terms below even
  though every vital in this repository is synthetic, because a hazard analysis
  that names its harms as "degraded UX" is not one.
- **Existing control** — the design measure already in the code that interrupts
  the sequence.
- **Residual risk** — what is left after the control, stated as what the control
  does _not_ reach.

Two harms run in opposite directions and are kept apart throughout. A **missed
alert** is a caregiver not learning of an event that happened. A **false alert**
is a caregiver responding to one that did not. They have different controls, and
tightening either one loosens the other. Alarm fatigue (H7) is the mechanism that
turns an excess of the second into an instance of the first, which is why it sits
in this table rather than in a usability backlog.

## What this table is missing

Named here rather than left to be noticed, because the gaps are the part a
reader who knows the standard checks first.

- **No probability, severity, or acceptability.** ISO 14971 asks for risk to be
  estimated and evaluated against criteria set in advance. Nothing here does
  that, and a table of hazards without it is half the method. Inventing
  likelihoods for a system nobody has used would be the exact fabrication
  [README.md](README.md) refuses.
- **No overall residual risk evaluation**, and no benefit-risk reasoning. Both
  require a device, an intended population, and a manufacturer.
- **Hazards found from defects, not from a systematic search.** These rows came
  from things that broke. A real analysis works the other way — a structured
  sweep over functions, interfaces, use errors and foreseeable misuse — and
  would find hazards this repository has not encountered yet. Two that such a
  sweep reaches immediately are a wearable whose battery dies and one carried
  out of BLE range; neither is in this table, and both are scored in
  [risk-register.md](risk-register.md) as H9 and H10.

  **Correction, C21.** This bullet used to read "the battery and BLE-range
  hazards the roadmap has been carrying since C4". `git log -S` against
  `docs/ROADMAP.md` shows it was **wrong in both directions at once**, which is
  the part worth recording. Battery was there _earlier_ than claimed: named in
  the **C21** row since the bootstrap commit `0b0308e`, never at C4. BLE range
  was not there _at all_ until `4b76c8b` — **which is C20, the commit that wrote
  this sentence.** It asserted the roadmap had carried a hazard since C4 in the
  same change that first put that hazard in the roadmap.

  C4's row names five failure modes — device disconnect, duplicate packets,
  delayed or out-of-order packets, clock drift, and offline buffering with
  replay — and neither hazard is among them. A sentence that misdates one item
  early and one item late is not approximately right and was not a slip in
  recall: it was written without opening the file it describes. Nothing in this
  repository checks a prose claim about another file, which is why it survived
  a commit whose whole argument was that citations should be machine-checked.

- **Use error is barely covered.** H8 is the only row about a person
  misunderstanding the system, and it addresses the copy rather than the
  interaction.
- **No traceability the other way.** Each row cites a test; no test cites a row,
  so a control can be deleted and the guard still passes as long as the test
  name survives.

## What C22's threat model found that this table does not carry

Added at C22 so a reader of this file learns what a reader of
[../security/threat-model.md](../security/threat-model.md) already knows: **that
model names three things about this table.** Two are absences and one is a route
into a row that is here.

- **An alert falsely marked triaged.** `actor` on a decision is a caller-asserted
  string, so an alert can be recorded acknowledged by a name that triaged
  nothing, and it then leaves the undecided set H2's control rations. H2 covers
  an untriaged alert being _discarded_; nothing here covers one being _falsely
  marked_, and the harm is the same missed alert.
- **The server itself exhausted.** Nothing bounds how many fan-out subscribers
  exist, so enough concurrent subscriptions end monitoring for every device at
  once. That reaches H4's harm by a route H4 never considered, since H4 is about
  one quiet device.
- **H4 reached by suppression rather than by failure.** Frames arriving for a
  device that has stopped reset its last-seen stamp, so it reads as alive and the
  silence sweep never fires. This is not a missing hazard — it is a residual H4
  does not currently name, and H4's residual now names it.
- **H2's harm at a third site, and the three states are the finding.**
  `apps/server/src/audit.ts` (C22) is a third bounded store that discards its
  oldest. It is not simply a repeat: it counts what it discards, where the
  decision log does not — but nothing serves that count, where the alert history
  is served on `GET /devices`. So the three sites sit in three states rather
  than two, and the middle one is where this repository now is:

  | Store                       | Eviction is     | Reachable by  |
  | --------------------------- | --------------- | ------------- |
  | alert history (`alerts.ts`) | counted, served | anyone, today |
  | audit log (`audit.ts`)      | counted         | nobody, today |
  | decision log (`acks.ts`)    | uncounted       | nobody, ever  |

  The audit log is genuinely better than the decision log and genuinely worse
  than the alert history, and the gap is a read path — no route serves it and no
  view shows it, so its events are **recorded and not detectable**. That read
  path is owed, and the row that closes C22 carries it beside the two register
  rows below.

- **H2's harm at a second site.** `apps/server/src/acks.ts` bounds its decision
  log at 200 events per device and splices the oldest away — the same forced
  eviction H2 is about, in a store H2 does not look at, and without the counting
  H2's control provides. This is a fourth shape: not an absence like the two
  above, and not a new route into a live row, but **an identified hazard with an
  unrecognised second instance**. Its disposition is therefore not the admission
  rule at all — eviction here is designed behaviour whose residual was never
  written down, so there is no candidate row owed. H2's residual now names it.

**Disposition, under this table's own admission rule.** The opening lines admit
a hazard only if it came from a defect that actually happened here and is pinned
by a test — the rule that put the battery and BLE-range hazards in the register
as `register-only` rather than here. The first two land on the same side: neither
has ever happened, neither has a control, and neither can be admitted without
suspending the rule. They belong where H9 and H10 already are — **owed as two
register rows, and the row that closes C22 carries that debt**, alongside the
sweep and prose-claims candidates C21 named, so it sits where owed work is
tracked rather than in a paragraph nobody re-reads. The third is
different in kind: H4 exists, so its residual is a row-level amendment rather
than an admission question, and the amendment is not made here because touching
that row's text would move it out of step with the register that cross-checks it.

**Both residuals are amended in this pass rather than across two commits.**
The correction that brought this section was already editing H2's residual, and
leaving H4's for later would have left one file half-amended with no reader able
to tell which half was current. That is a batching decision, not a finding.

**Why one suppression route lands here and the other stays in the threat model.**
A hazard analysis covers faults; a threat model covers adversaries. The same
outcome — a stopped device reading as alive — is reachable both ways, so it is
written in both places and each carries the half it owns. Here it is a
`deviceId` collision: the field is caller-asserted, nothing prevents two
gateways claiming one, and a misconfigured duplicate keeps the stamp fresh while
the real device is dead. In [../security/threat-model.md](../security/threat-model.md)
it is TH1, where somebody forges the stream on purpose. Neither document is the
right home for both halves.

**This section is prose and no guard reads it.** `scripts/check-hazard-tests.sh`
checks that the rows above cite tests that run; it has nothing to say about
whether this paragraph is true or whether the threat model still says what it
says. That is the same limit the threat model states about its own hazard
citations, and it is the third document in this repository to say so.

C21 builds the register these rows feed, with the columns this table does not
have.
